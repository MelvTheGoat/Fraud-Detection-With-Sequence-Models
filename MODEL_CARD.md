# Model card — transaction fraud scoring

This card describes the models in this repository. **They are trained on
synthetic data and must not be deployed against real payment traffic.** The
synthetic generator encodes one author's assumptions about how fraud works;
those assumptions are visible in `src/simulate.py` and they are not a substitute
for a real portfolio.

Numbers quoted here come from `results/` and are regenerated by
`python -m src.experiment`. Run `python -m src.report` to reproduce the tables.

---

## Model details

| | |
| --- | --- |
| **Developed by** | This repository (research/demonstration project) |
| **Model type** | Binary classifiers over per-customer transaction sequences, plus a gradient-boosted tree baseline |
| **Architectures** | GRU, dilated causal TCN, small causal Transformer encoder, LightGBM |
| **Input** | The 32 most recent transactions of one customer, ending with the transaction being authorised |
| **Output** | Probability that the transaction is fraudulent, plus a decision (`approve` / `review` / `block`) |
| **Framework** | PyTorch (sequence models), LightGBM (baseline), ONNX Runtime (serving) |
| **Licence** | See repository |
| **Version** | 0.1.0 |

### Sizes and training cost

All models are deliberately small enough to train on a laptop CPU or a free
Colab/Kaggle session. Parameter counts and training times are reported in
`results/summary.json` and reproduced in the README's architecture table.

The embedding tables dominate the parameter count — the merchant table alone is
roughly 47k of it. That matters when reading a headline parameter count: most of
these models is a lookup table, not computation.

## Intended use

### In scope

- Demonstrating and comparing sequence architectures against a strong tabular
  baseline on a fraud-shaped problem.
- Teaching material for temporal leakage, calibration under class imbalance,
  cost-sensitive thresholding, and adversarial drift monitoring.
- A starting skeleton for a real system: the pipeline structure, the online/
  offline parity contract, and the evaluation harness are the transferable parts.

### Out of scope

- **Any real financial decisioning.** The models have never seen real
  transactions.
- **Deciding about individuals.** Nothing here is validated for fairness across
  protected characteristics; the synthetic data has no demographic attributes at
  all, so the question could not even be asked of it.
- **Transfer to another portfolio without retraining.** The merchant, device-type
  and country vocabularies are fitted to one synthetic population. A merchant
  code from elsewhere maps to the "unknown" embedding.

## Training data

Synthetic, generated by `src/simulate.py`. Roughly 300k transactions across
2,500 customers over 180 days, with a fraud rate near 0.65%.

Three fraud mechanisms with known labels:

- **Card testing** — a burst of small authorisations validating a stolen number.
- **Account takeover** — a behavioural break from the customer's own baseline.
- **Merchant compromise** — cards breached at one merchant, cloned and used
  elsewhere days later.

Realistic confounders are injected deliberately: multi-device customers, phone
upgrades, one-off devices, legitimate small-purchase bursts, travel, and a heavy
amount tail. Without them the problem is separable and the comparison measures
nothing (see DECISIONS.md §2.1).

4% of fraudulent transactions carry a legitimate label, representing fraud the
customer never disputed. This caps achievable recall, as it does in reality.

**Adversarial drift** is injected in the final 15% of the timeline: every
mechanism adapts against its own obvious defence.

### Splits

Temporal, never random: 60% train / 15% validation / 25% test, with a one-day
embargo between splits. The test window straddles the drift boundary, so
aggregate test numbers average two quite different regimes; the README reports
them separately.

## Evaluation

### Metrics used

- **PR-AUC** — ranking quality with a rare positive class.
- **Precision and recall at review capacity** (top 0.1% / 0.5% / 1%) — the alert
  budget a fraud team can actually work.
- **Per-mechanism recall** — which attacks each model catches, and which it is
  blind to.
- **Expected cost per transaction** — the headline, with both error costs
  parameterised.
- **Brier score, ECE, reliability diagrams** — whether the probabilities mean
  anything.

### Metrics deliberately not used

**Accuracy.** At a 0.65% fraud rate, predicting "never fraud" is about 99.35%
accurate and so is every model worth deploying. Every evaluation in this
repository reports accuracy directly next to the accuracy of the always-legitimate
predictor, so the reader can see they are the same number.

**ROC-AUC as a headline.** Reported, but it is optimistic under extreme imbalance
because the false-positive rate barely moves when negatives dominate.

## Limitations

### Of the models

- **Bounded history.** Every feature looks back at most 31 transactions, so
  long-horizon signal (true tenure, lifetime spending baseline) is unavailable.
  This buys exact online/offline parity from a stateless service; the trade-off
  is discussed in DECISIONS.md §4.1.
- **No cross-customer structure.** Merchant compromise is fundamentally a graph
  phenomenon — shared merchants and devices across customers. These models see it
  only through one customer's own history.
- **Calibration is fitted on validation and can go stale.** The isotonic map is
  fitted once. Under drift, the probabilities degrade before the ranking does.
- **Optimistic recall accounting.** Fraud arrives in episodes; a card-testing
  burst is 5–14 transactions and the later ones are easy because the earlier ones
  are already in the window. Reported recall is therefore better than
  "did we catch this attack early" would be. See DECISIONS.md §11.

### Of the evaluation

- **One synthetic population, one seed for the data.** Model seeds vary (three
  per arm) but the dataset does not. Conclusions are specific to this generator.
- **Costs are assumed, not measured.** The false-positive cost in particular is
  unknowable in the abstract; the README reports a sensitivity sweep across a 15x
  range rather than a single number.

### Of the interpretability

- **Attention is not explanation.** Attention weights show where the model read
  from, not why it decided; a low-weight position can be decisive and a
  high-weight one inert. They are presented as pointers to related activity for
  an analyst, always alongside a gradient attribution.
- **SHAP and attention are not comparable quantities.** TreeSHAP is exact and
  additive in log-odds; the sequence attributions are first-order and spread over
  positions.

## Ethical considerations

A fraud model declines people's payments. Two consequences shape the design here.

**False positives are a real harm, not a metric.** A declined card at a
supermarket till is an embarrassment, a declined card abroad is a crisis. The
cost model prices false positives explicitly rather than treating recall as the
only thing that matters, and the sensitivity analysis shows how the operating
point moves as that price changes.

**Every decision is auditable.** The service writes an append-only record of each
decision — score, threshold, model version, contributing transactions — before it
returns a response, because a customer who complains months later deserves an
answer that does not depend on re-running a model that has since changed.

**Fairness is not evaluated here and that is a gap, not a clean bill of health.**
The synthetic data carries no demographic attributes, so no disparity analysis is
possible. A real deployment must measure decline rates and review rates across
protected groups, and must consider proxies: device type correlates with income,
merchant category correlates with lifestyle, and geography correlates with
almost everything. A model can be blind to a protected attribute and still
discriminate through them.

**Adversarial pressure is a safety property, not just a metric.** The monitoring
section exists because a fraud model that has silently stopped working is worse
than no model: it produces confident approvals for attacks it can no longer see.

## Maintenance

- **Retraining.** The temporal split means a deployed model is always scoring
  data later than anything it trained on. Fraud drift is adversarial and fast;
  the monitoring signals in `src/monitoring.py` are the trigger.
- **What to watch.** The alert rate at the fixed production threshold is the
  leading signal here. Score PSI, the conventional choice, is close to blind on
  this problem — see DECISIONS.md §10.1.
- **What breaks first.** Calibration, then per-mechanism recall on whichever
  attack the adversary is currently adapting, then aggregate ranking. Aggregate
  metrics are the last thing to move and the worst thing to wait for.
